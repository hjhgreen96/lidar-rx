# `clock` - 센서 시계에서 호스트 시계로

포인트의 측정 시각은 센서 시계로 찍혀 온다. 로봇의 다른 센서(IMU, 휠, 카메라)와 합치려면 모두가 공유하는
호스트 시계로 옮겨야 한다. 이 크레이트는 패킷마다의 (센서 시각, 커널 수신 시각) 쌍으로 두 시계의
관계를 추정한다.

```text
 crates/clock/src/
 ├── lib.rs     ClockEstimator (창, 다시 맞추기, 계단 감지), ClockModel (변환), Config
 ├── fit.rs     직선 맞추기 두 가지: least_squares, lower_envelope (+ 아래쪽 볼록 껍질)
 └── tests.rs   정답을 아는 합성 데이터
```

## 1. 추정 대상

```text
 센서가 패킷을 찍은 시각 s (센서 시계)     →  네트워크·커널  →  커널이 받은 시각 h (호스트 시계)

 h = s + (두 시계의 차이) + 지연
          └─ 시간에 따라 천천히 변함:  차이(s) = 오프셋 + 기울기 × s
             기울기(skew) = 두 시계의 빠르기 차이. 1 ppm = 1초에 1 µs씩 벌어짐
```

점 하나 = 패킷 하나. 그래프로 그리면:

```text
  y = h − s  (µs)
  ▲
  │        ·    ·  ·          ·     ·   ·     ·   ← 늦게 온 패킷들 (지연이 큼)
  │   ·  ·   ·  ·   ·  ·  ·  ·  ·  ·  ·  ·  ·
  │ ·  ·  ·  ·  ·  ·  ·  ·  ·  ·  ·  ·  ·  ·  ·
  │●──●───●──●───●──●───●──●───●──●───●──●───●── ← 가장 빨리 온 패킷들 = 두 시계의 차이 + 최소 지연
  └──────────────────────────────────────────────► x = s (센서 시각)
     기울기 = skew
```

`Frame`에는 프레임을 이룬 패킷들의 (센서 시각, 수신 시각)이 `packet_times`로 실려 온다. `stamp_frame`이 이
쌍들을 모두 넣고, 프레임 대표 시각(`sensor_stamp`)을 호스트 시각으로 바꿔 `Frame::stamp`에 채운다.

## 2. 평균 대신 하한선을 쓰는 이유

수신 지연은 음수가 될 수 없다. 패킷은 늦게 올 수는 있어도 일찍 올 수는 없다. 그래서 점들은 실제 관계의
직선 위쪽에만 흩어진다.

| 방법 | 추적 대상 | 문제 |
|---|---|---|
| 최소제곱 | 점들의 한가운데 | 평균 지연만큼 위로 밀림. 늦은 패킷 몇 개(혼잡)가 직선을 끌어올림 |
| **하한선** | 점들의 아래쪽 경계 = 가장 빨리 온 패킷들 | 늦은 패킷은 아무리 늦어도 영향이 없음 |

근거가 있는 방법이다:

- Moon, Skelly, Towsley, "Estimation and Removal of Clock Skew from Network Delay Measurements",
  INFOCOM 1999 - 네트워크 지연 측정에서 두 시계의 기울기를 선형계획으로 추정. 여기서 구현한 식.
- Olson, "A Passive Solution to the Sensor Synchronization Problem", IROS 2010 - 로봇 센서 동기화에서 같은
  원리(지연은 음수가 아니다)를 씀.

## 3. 하한선 계산: 아래쪽 볼록 껍질

Moon 외의 문제:

```text
 모든 점 아래(이하)에 있으면서         yᵢ ≥ a·xᵢ + b   (모든 i)
 점들과의 세로 거리 합이 가장 작은 직선   Σ (yᵢ − a·xᵢ − b)  최소

 Σ (yᵢ − a·xᵢ − b) = n · (ȳ − (a·x̄ + b))
   → ȳ는 정해져 있으므로 "x̄ 위치에서 직선이 가장 높을 것"과 같은 문제
   → 모든 점 아래에 있으면서 x̄에서 가장 높은 직선 = 아래쪽 볼록 껍질의 변 중 x̄를 가로지르는 변
```

```text
     ·          ·        ·
   ·    ·  ·       ·  ·     ·   ·
  ●─────────●──────────────●─────────●      ● : 아래쪽 볼록 껍질의 꼭짓점
             ╲     x̄      ╱                  x̄를 가로지르는 변(●──●)을 늘인 직선이 답
```

반복 최적화가 필요 없다. 점들이 이미 x(센서 시각) 순서이므로 껍질은 한 번 훑어서 만든다 (Andrew의
monotone chain, O(n)):

```text
 lower_hull: 왼쪽부터 점 p를 보며
   while 껍질의 마지막 두 꼭짓점 → p 가 왼쪽(반시계)으로 꺾이지 않으면: 가운데 꼭짓점을 버림
   p를 넣음
 꺾임 판정: 외적 cross(o, a, b) = (a.x − o.x)(b.y − o.y) − (a.y − o.y)(b.x − o.x) > 0 이면 왼쪽
```

코드: `fit::lower_hull`, `fit::lower_envelope`. 비교용 `fit::least_squares`는 표준 공식.

## 4. 실행 중 추정: `ClockEstimator`

```text
 observe(s, h)
   ├─ s가 지난 값과 같거나 조금 뒤 (경계 패킷 중복, 순서 바뀜)   → 무시 (ignored)
   ├─ s가 10 ms 넘게 뒤로 감 (재생 반복, 센서 재시작)             → 리셋
   ├─ 지금 직선보다 5 ms 넘게 아래                                → 리셋 (호스트 시계가 뒤로 뜀)
   ├─ 지금 직선보다 5 ms 넘게 위인 상태가 1 s 이상 계속            → 리셋 (호스트 시계가 앞으로 뜀)
   │     잠깐(1 s 미만) 위로 뜬 것은 혼잡으로 보고 그대로 둠
   ├─ 점 추가 (x = s − s₀, y = (h − s) − 기준)   ← f64 정밀도를 위해 첫 점 기준 상대값
   └─ 754개마다(약 1초): 창(30 s) 밖의 점을 버리고 다시 맞춤 (하한선 + 최소제곱)
                         첫 추정은 2 s 분량이 쌓인 뒤
```

| `Config` | 기본값 | 이유 |
|---|---|---|
| `window_us` | 30 s | 기울기는 온도 등으로 천천히 변함 → 오래된 점은 버림 |
| `refit_every` | 754 (약 1 s) | 껍질 계산은 O(n)이지만 매 패킷마다 할 필요는 없음 |
| `min_span_us` | 2 s | 너무 짧은 구간의 기울기는 부정확 |
| `step_threshold_ns` | 5 ms | 정상 흔들림(샘플에서 최대 약 1.2 ms)보다 충분히 큼 |
| `step_persist_us` | 1 s | 혼잡과 시계 계단을 구분 |

계단이 실제로 생기는 경우: 호스트 시계(`CLOCK_REALTIME`)는 NTP가 한 번에 옮길 수 있다. RTC 배터리가
없는 보드(Arty Z7)는 부팅 직후 NTP 동기화 때 시계가 크게 뛴다.

정밀도: 호스트 시각(ns)은 약 1.7 × 10¹⁸으로 f64가 정확히 나타내는 정수 범위(9 × 10¹⁵)를 넘는다.
그래서 첫 점을 기준으로 뺀 상대값(`Origin::relative`)으로 계산한다.

### 비용 - 보드에서 드러난 것 (2026-11-11)

다시 맞추기는 창 안의 점 전부(30 s × 754 = 22,620개)를 몇 번 훑는다: 껍질, 최소제곱, 잔차. PC에서는 1 ms 미만이라
보이지 않았지만, 보드(Cortex-A9 650 MHz)에서 재 보니 20 ms였다 (`cargo run --release -p clock --example refit_cost`,
754 pkt/s로 40초 분량을 넣으며 1초마다 가장 오래 걸린 `observe`):

| 창 안의 점 | PC (x86, WSL) | 보드 처음 | 보드: 잔차 분위수를 정렬 대신 선택으로 |
|---|---|---|---|
| 2,262 (3 s) | 0.07 ms | 1.17 ms | 0.60 ms |
| 11,310 (15 s) | 0.35 ms | 8.99 ms | 4.60 ms |
| 22,620 (30 s, 가득) | 0.97 ms | **20.94 ms** | **10.52 ms** |

- 잔차는 p50·p99·최대 세 값만 쓰므로 전부 정렬(O(N log N))하지 않고 그 순위만 고른다(`select_nth_unstable`, O(N)).
  잔차 버퍼도 매번 새로 할당하지 않는다. 값은 정렬할 때와 같다 (원본 캡처의 잔차 p99 337.4 µs, 최대 1218.6 µs 그대로).
- 그래도 O(N)이라 10 ms가 남는다 (A9의 배정밀도 연산·메모리 대역). 그래서 이 일을 수신 스레드에서 뺐다: lidar-rx의
  threaded 모드에서는 stage 스레드(일반 정책)가 `stamp_frame`을 부른다 ([rx.md](rx.md)). 실시간 정책을 받는 수신 스레드에는
  패킷마다 상한이 정해진 일만 남는다. 다시 맞추는 동안 늦어지는 것은 프레임 전달(stage)뿐이고 소켓 큐는 아니다.
- 더 줄이려면: 1초 묶음마다 껍질과 최소제곱 합을 미리 만들어 두고 다시 맞출 때는 묶음 30개만 합치는 방식이 있다
  (껍질은 묶음별 껍질의 합집합의 껍질과 같다). 잔차 분위수만 따로 처리하면 된다. 지금은 하지 않았다.

## 5. 남는 오차

```text
 하한선 = 두 시계의 차이 + (가장 빨리 온 패킷의 지연)
                           └─ 센서가 12블록을 모으는 시간(약 1.33 ms) + 전송 + 커널 처리
```

한쪽 방향(센서 → 호스트) 측정만으로는 이 최소 지연을 잴 수 없다. 기울기는 정확히 나오지만, 오프셋에는
최소 지연만큼의 상수가 남는다. PTP(IEEE 1588)는 왕복 메시지로 경로 지연까지 재서 이 상수를 없앤다.
이 추정은 PTP·GPS가 없을 때의 소프트웨어 방법이다.

## 6. 결과

### 원본 캡처 파일 (`lidar-rx --pcap data/vlp16.pcap`)

호스트 시각 = 원래 캡처 PC의 커널이 찍은 캡처 시각.

| 항목 | 값 |
|---|---|
| 기울기 (하한선) | −53.457 ppm |
| 기울기 (최소제곱) | −53.352 ppm |
| 최소제곱이 하한선보다 위 | 233.9 µs (평균 추가 지연) |
| 하한선 위 거리 | p50 231.6 µs, p99 337.4 µs, 최대 1218.6 µs |
| 점 | 6,787개, 9.01 s |

−53 ppm이면 1시간에 약 0.19 s 벌어진다 → 한 번 맞추고 끝내면 안 된다. 이 값은 원래 캡처 환경(센서와 캡처 PC)의
성질이고, 어느 쪽 시계가 틀린지는 이 데이터만으로 알 수 없다.

### 정답을 아는 시험 (`tools/known_drift.sh`, WSL loopback)

`pcap-replay --pace sensor --drift-ppm 100`: 센서 시각 간격 × (1 + 100 ppm)으로 보냄. 센서 시각으로 1초인 간격을
이 컴퓨터 시계로 1.0001초에 걸쳐 보내므로, 센서 시계가 이 컴퓨터 시계보다 100 ppm 느린 상황이다. 보내는 쪽과 받는
쪽이 같은 시계라, 받는 쪽이 보는 기울기는 정확히 +100 ppm이어야 한다 (양수 = 호스트 시계가 더 빠름).

| 항목 | 실행 기록 ([2-rx-clock-ros2.md](../runs/2-rx-clock-ros2.md)) |
|---|---|
| 기울기 (하한선) | **+100.019 ppm** |
| 기울기 (최소제곱) | +99.971 ppm |
| 하한선 위 거리 | p50 1.0 µs, p99 14.2 µs, 최대 1.4 ms |
| 점 | 21,113개, 28.02 s (3회 반복) |

같은 시험을 여러 번 돌린 하한선 기울기: +100.014, +100.016, +100.017, +100.019 ppm - 모두 +100.01 ~ +100.02 안이다.
최소제곱은 +99.94 ~ +99.99로 더 흔들린다. 하한선 위 거리의 최대값(0.4 ~ 2.9 ms)이 실행마다 다른 것은 송신
쪽(WSL 가상 머신)이 가끔 늦게 보내기 때문이다. 하한선은 늦은 점에 영향을 받지 않는다.

### 원래 간격 그대로 다시 보내기 (`pcap-replay --pace capture`, 반복 없이)

replay가 원래 캡처 시각 간격대로 보내면, 받는 쪽은 원래 캡처 PC와 센서 사이의 관계를 다시 보게 된다.

| 항목 | 파일을 직접 분석 | 다시 보내서 받은 것 (실행 기록) |
|---|---|---|
| 기울기 (하한선) | −53.457 ppm | −53.527 ppm |
| 최소제곱이 하한선보다 위 | 233.9 µs | 236.1 µs |

다시 보내서 받은 기울기는 실행마다 −53.1 ~ −53.5 ppm으로, 파일을 직접 분석한 값과 0.4 ppm 안에서 같다. 차이는
replay가 보낸 시각의 흔들림(대부분 수 µs, 가끔 ms)과 받는 쪽 지연이 더해진 것이다. 9초짜리 한 번이라 +100 ppm
시험(28초, 송신 간격에 흔들림 없음)보다 흔들림이 크다. 이 −53 ppm은 원래 캡처 환경의 성질이지 이 PC의 성질이
아니다 - 슬라이드에서 둘을 섞지 않는다.

## 7. 테스트

정답: 호스트 = 센서 × (1 + 100 ppm) + 상수, 관측 = 정답 + 최소 지연 50 µs + 추가 지연(평균 200 µs 지수 분포,
1% 확률로 2 ms).

| 테스트 | 확인하는 것 |
|---|---|
| `fit::exact_line_is_found_by_both` | 잡음 없으면 두 방법 모두 정확 |
| `fit::envelope_ignores_positive_noise_least_squares_does_not` | 위쪽 잡음: 하한선은 정확, 최소제곱은 평균 지연만큼 밀림 |
| `fit::hull_keeps_only_lower_corners` | 껍질 꼭짓점 |
| `recovers_known_skew_and_offset` | 기울기 ±0.5 ppm, 오프셋 = 정답 + 최소 지연 ±10 µs, 최소제곱 치우침 150~300 µs |
| `host_clock_stepping_back_resets_immediately` | −50 ms 계단 → 리셋 1회, 다시 추정 |
| `host_clock_stepping_forward_resets_after_it_persists` | +50 ms 계단 → 1 s 뒤 리셋 |
| `short_congestion_is_not_a_step` | 0.5 s 동안 20 ms 늦음 → 리셋 안 함 |
| `duplicates_are_ignored_and_a_big_backward_jump_restarts` | 중복 무시, 재생 반복 → 리셋 |
| `needs_two_seconds_before_the_first_estimate` | 첫 추정 시점 |
